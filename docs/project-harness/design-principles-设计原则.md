# 设计原则

## 1. 从最小结构开始

默认只创建 `AGENTS.md` 和 `PROJECT_STATE.md`。其他文件必须由真实项目需求触发。

## 2. 当前状态与长期知识分离

- 当前目标、进展和下一步进入 `PROJECT_STATE.md`。
- 稳定决策进入 `DECISIONS.md`。
- 重复流程进入 `RUNBOOK.md`。
- 外部资料进入 `REFERENCES.md`。
- 重复错误和改进经验进入 `LESSONS_LEARNED.md`。

## 3. 状态不是历史流水账

状态文件只保存下一轮继续工作真正需要的当前真相。完成历史可以由 Git、归档或专门记录承载。

## 4. 按需拆分任务状态

只有多个任务并行、单个任务跨多轮推进，或根状态文件已经明显膨胀时，才创建 `task-states/`。

## 5. 先形成流程契约，再升级 Skill

一个流程仍依赖用户逐步盯梢时，先定义输入、输出、自检、下游验收和返工规则。只有真实重复使用后，才考虑脚本化或 Skill 化。

## 6. 高风险动作始终保留人类确认门

删除、覆盖、移动、发布、外部写入、权限、账号和付费资源操作不能因为流程成熟而绕过确认。

## 7. 保持单项目边界

Project Harness 管理一个项目内部的执行约束。跨项目优先级、资源调度和 Portfolio 管理应由独立系统承担。
