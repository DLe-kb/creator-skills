# Project Harness 项目脚手架手册

Project Harness 是单个项目内部的轻量约束系统，用来让 Codex / Agent 在新对话中快速知道：项目是什么、当前做到哪里、哪些不能动、下一步怎么推进、什么时候需要人确认。

它的目标是减少上下文重建、误操作和返工，不是制造文档负担。

## 核心原则

只保留能降低未来成本的信息。一个文件、规则或流程如果不能帮助下一轮 Agent 更快恢复上下文、更少误操作、更少返工，就不要放进 Harness。

默认从小开始：

```text
AGENTS.md
PROJECT_STATE.md
```

按真实需求升档：

```text
RUNBOOK.md              有重复流程或阶段契约时创建
DECISIONS.md            有稳定决策时创建
DISCUSSION_QUEUE.md     有需要用户判断的问题时创建
REFERENCES.md           有重要资料和链接时创建
LESSONS_LEARNED.md      有重复错误或复盘经验时创建
task-states/            状态文件过长或多任务并行时创建
```

不要为了“完整”复制全部模板。

## 三个核心文件

### AGENTS.md

放稳定入口和边界：

- 项目是什么。
- 默认语言和文件命名偏好。
- 继续项目时先读哪些文件。
- 哪些目录或资料不能改。
- 删除、覆盖、移动、发布、外部写入、权限和账号操作前必须确认。
- 默认完成标准。

不要放每日进度、长历史、完整操作流程或大段方法论。

### PROJECT_STATE.md

放当前真相：

- 当前目标。
- 当前状态。
- 活跃任务索引。
- 下一步。
- 活跃文件。
- 阻塞项。
- 需要用户决策的问题。

它应短、准、当前。不要写成任务流水账。稳定决策放 `DECISIONS.md`，重复流程放 `RUNBOOK.md`，资料放 `REFERENCES.md`，经验放 `LESSONS_LEARNED.md`。

### RUNBOOK.md

放成熟、可重复的流程：

- 安装、配置、检查、发布、迁移、清理等操作步骤。
- 外部工具和 API 的安全流程。
- 成熟流程的阶段契约、自检、下游验收和返工闭环。

不要把所有工作方法都写进 RUNBOOK。只写已经跑过、以后还会重复的流程。

## 按需扩展文件

- `DECISIONS.md`：已经确定、后续不再反复讨论的判断。
- `DISCUSSION_QUEUE.md`：Codex 不应擅自决定、需要用户判断或授权的问题。
- `REFERENCES.md`：官方文档、工具链接、研究记录、外部资料。
- `LESSONS_LEARNED.md`：重复错误、协作摩擦、流程改进经验。
- `task-states/*.md`：某个活跃任务跨多轮推进，且根 `PROJECT_STATE.md` 已不适合承载细节时使用。

## task-states 启用条件

只有满足以下条件之一时才启用：

- `PROJECT_STATE.md` 大约超过 150-200 行，并开始拖慢上下文恢复。
- 两个或更多任务并行活跃。
- 某个子任务会跨多轮推进，且有独立目标、文件、阻塞项和完成条件。
- 用户明确要求按任务拆分状态。

启用后，`PROJECT_STATE.md` 只保留项目总览和活跃任务索引。只读取当前相关任务状态，不默认读取所有历史任务。不预先创建空任务文件。

## 单轮任务流程

每轮任务按这个顺序推进：

```text
明确目标
-> 只读检查
-> 判断风险和确认点
-> 小步执行
-> 验证证据
-> 必要时更新 Harness
```

需要停下来确认的动作：

- 删除、覆盖、移动关键文件。
- 修改权限或转移所有权。
- 外部账号写入或真实发布。
- 使用付费资源或高成本批处理。
- 方向性改变。
- 返工达到上限仍无法解决。

普通步骤只要在项目规则、runbook 或用户已确认范围内，并且不触发以上风险，可以自动推进并记录证据。

## 阶段契约和返工闭环

成熟流程如果仍需要用户逐步盯梢，优先在 `RUNBOOK.md` 中写阶段契约，而不是新建复杂 skill。

每个阶段只需写清：

```text
阶段：
输入标准：
输出标准：
自检清单：
下游验收：
证据：
返工规则：
返工上限：
用户确认门：
```

执行循环：

```text
阶段执行
-> 自检
-> 记录证据
-> 下游验收
-> 合格：进入下一阶段
-> 不合格：写返工单并回到对应阶段
-> 达到返工上限：升级给用户
```

证据必须具体，例如测试输出、截图、抽样时间点、文件数量、缺失字段、分辨率、抽帧路径或检查清单结果。不要只写“已检查”。

## Skill 化原则

重复流程先进入项目 `RUNBOOK.md` 或知识库。只有在真实使用 2-3 次后，输入输出稳定、边界清楚、验证证据明确，才考虑升级为 skill、脚本、MCP 或 automation。

过早 skill 化会让系统臃肿。删除过重 skill 时，应把仍有价值的方法论沉淀到知识库，而不是换个名字继续保留。

## 新对话启动话术

只恢复上下文：

```text
请从这个项目继续。先读取 AGENTS.md 和 PROJECT_STATE.md。
如果 PROJECT_STATE.md 指向了当前活跃的 task-states 文件，只读取相关任务状态。
然后用 5-10 行告诉我当前目标、最近进展、下一步和需要我决策的问题。
在我确认前不要改文件。
```

直接推进：

```text
请从项目状态恢复上下文，直接推进当前下一步。
执行前先做只读检查；如果涉及删除、覆盖、移动、联网安装、外部写入、发布、权限或账号操作，先停下来说明原因并请求确认。
完成后检查是否需要更新 PROJECT_STATE.md、DECISIONS.md、DISCUSSION_QUEUE.md、REFERENCES.md、RUNBOOK.md 或 LESSONS_LEARNED.md。
```
